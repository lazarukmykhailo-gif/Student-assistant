# Аналіз технічного завдання проєкту «Student Assistant»

## Функціональні вимоги
- Відображення списку навчальних завдань із їхніми назвами, дедлайнами (`dueDate`), пріоритетами (`priority`) та статусом виконання (`completed`).
- Створення нових завдань, редагування наявних параметрів та зміна статусу виконання (відмітка про завершення).
- Фільтрація та сортування завдань за статусом виконання, рівнем пріоритету (`low`, `medium`, `high`) та терміном здачі.
- Збереження та зчитування спільного масиву даних у форматі JSON для синхронної роботи різних клієнтів.
- Аналітика продуктивності студента: підрахунок відсотка виконаних завдань, кількості прострочених задач та розподілу за пріоритетами.

## Нефункціональні вимоги
- **Кросплатформність:** коректна робота клієнтських застосунків на різних операційних системах (Windows, Linux, macOS) та у сучасних веббраузерах.
- **Єдиний формат даних:** сувора сумісність усіх модулів зі схемою файлу `data/tasks.json` у кодуванні UTF-8 без пошкодження структури.
- **Продуктивність та чуйність:** швидкий запуск нативного ядра та миттєве оновлення інтерфейсу під час зміни фільтрів чи статусу завдань.
- **Зручність використання (UX):** інтуїтивно зрозумілий графічний інтерфейс, візуальне виділення пріоритетів і наближених дедлайнів.

## Модулі та технології
| Модуль | Директорія | Технології | Призначення |
| :--- | :--- | :--- | :--- |
| Вебклієнт | `frontend/` | React, JavaScript/TypeScript, HTML/CSS | Інтерактивний вебзастосунок для керування списком завдань у браузері |
| Десктоп-контейнер | `desktop-container/` | Electron / NW.js | Обгортання вебклієнта у кросплатформний настільний застосунок із доступом до файлової системи |
| Нативне ядро | `cpp-core/` | C++, Qt | Високопродуктивний нативний клієнт та обробка базової логіки |
| Аналітичний модуль | `python-analytics/` | Python, Flet | Статистичний аналіз успішності, візуалізація прогресу та звітність |
| Спільні дані | `data/` | JSON (`tasks.json`) | Єдине сховище даних про завдання для всіх клієнтів системи |

## Формат обміну даними
Усі клієнти проєкту працюють зі спільним файлом `data/tasks.json`, який являє собою JSON-масив об'єктів. Кожен об'єкт описує одне навчальне завдання та має фіксовану структуру полів:
- `id` (число) — унікальний ідентифікатор завдання;
- `title` (рядок) — текстовий опис або назва завдання;
- `completed` (логічне значення `true`/`false`) — позначка про виконання;
- `dueDate` (рядок у форматі `YYYY-MM-DD`) — кінцевий термін виконання;
- `priority` (рядок: `"low"`, `"medium"`, `"high"`) — рівень пріоритету завдання.

## Відкриті питання
1. Як саме має вирішуватися конфлікт одночасного запису у файл `data/tasks.json`, якщо користувач відкриє одночасно два клієнти (наприклад, нативний C++/Qt та аналітичний Python/Flet)?
2. Чи передбачена автоматична валідація JSON-схеми під час запуску клієнтів, якщо файл `tasks.json` був пошкоджений або містить неповний набір полів?
3. Чи потрібно реалізовувати сповіщення (нагадування) про наближення дедлайну (`dueDate`) у десктопній та нативній версіях?
4. Який мінімальний набір графіків чи метрик має генерувати модуль `python-analytics`?
